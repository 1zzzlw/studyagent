# StudyAgent 学习文档

## 目标

为 `studyAgent` 编写“先理解、再亲手练习”的学习材料。默认交付学习文档和 Notebook 练习说明，让学习者在自己的 `.ipynb` 中逐步实现，而不是一次生成整套代码。

创建或大幅调整学习模块时，先阅读 [学习文档模板](references/learning-document-template.md)。

## 默认交付边界

每次新增学习模块，默认只创建或更新：

- 模块目录下的 `README.md`；
- 模块目录下按章节组织的 Markdown 文档；
- 根目录 `README.md` 中受影响的学习路线、模块编号、完成状态和每日计划。

除非用户明确要求，否则不要：

- 创建完整的 `.py` 实现、测试套件或示例工程；
- 生成已经填好答案的完整 Notebook；
- 修改学习者已有的 `.ipynb` 文件；
- 为了演示而批量生成多个代码文件；
- 改动 `WildAgent` 或其他仅供参考的项目。

文档中可以提供单个知识点所需的短代码片段、方法签名和带 `TODO` 的练习骨架，但必须把实际输入、运行、观察和总结留给学习者在 Notebook 中完成。

如果用户明确要求“代码写详细，但不要创建代码文件”，就在 Markdown 中提供聚焦于当前知识点的详细代码，并按 `Cell 1`、`Cell 2`、`Cell 3` 拆开。默认练习载体是学习者自己维护的 `.ipynb`，不要建议创建 `.py` 测试文件、`tests/` 或 `manual_tests/`。每个 Cell 都要标明输入、依赖的前序 Cell、预期输出和观察点；详细示例只覆盖当前概念，不扩展成完整应用。

## 判断资料来源

先根据用户要求选择一种模式：

### 独立技术学习模块

当模块用于学习 Chroma、LangChain、Python 等独立技术时：

- 以当前项目安装版本和官方文档为依据；
- 对可能变化的 API，先检查 `pyproject.toml`、锁文件或实际安装版本，再查官方一手资料；
- 不要主动套用 `WildAgent` 的代码结构或业务设计。

### 项目源码导读模块

只有用户明确要求结合 `WildAgent` 时：

- 只读扫描其真实目录、入口、调用链、配置和测试；
- 在文档中区分“源码中已经实现”“学习用简化示例”“建议或待办”；
- 未获明确授权时，不修改 `WildAgent` 中的任何文件。

## 工作流程

1. 检查 `studyAgent` 根目录 `README.md`、现有模块目录、依赖文件和 `git status`，识别已有编号与用户文件。
2. 明确本次是新增模块、调整章节、重命名模块，还是只补充某一篇文档；发现编号冲突时先说明影响。
3. 设计从最小可运行概念到完整认知链路的章节顺序。先讲核心路径，再讲观察与排错，最后讲进阶内容。
4. 创建模块 `README.md` 和章节文档。每一章都必须给出可在 Notebook 中完成的分单元格练习方案。
5. 新增、删除、重命名或改变模块定位后，同步更新根目录 `README.md`。
6. 检查链接、编号、旧名称、实现状态和计划描述是否一致，并确认没有覆盖已有 Notebook。

## 文档写法

每个模块先回答：

- 这个模块解决什么问题；
- 它在总体学习路线中的位置；
- 学完后能独立完成什么；
- 哪些代码由学习者在 Notebook 中亲手编写。

每一章至少包含：

- 学习目标与前置知识；
- 核心概念和必要 API；
- 一个足够小的示例或伪代码；
- Notebook 分单元格练习步骤；
- 应观察的返回值、对象状态、日志或数据库变化；
- 一个主动制造的错误及其排查方向；
- 与正文相关的补充知识点，不额外布置章节练习题；
- 可验证的完成标准。

当一章并列介绍多种创建方式、客户端、存储后端或调用模式时，不能只给构造对象的代码。每一种方式都应分别给出一个简单、可观察的最小使用闭环，例如“创建对象 → 插入一次数据 → 查询一次数据 → 打印关键结果”，并注明运行前提、数据保存位置和该方式特有的错误。示例保持短小，可以重复基础步骤以保证每种方式都能独立理解。

避免把大量代码埋在文档里。一个片段只解释一个概念；如果代码已经接近完整答案，改成步骤、接口提示或 `TODO`。

默认不要在章节末尾设置“练习题”“思考题”或要求学习者继续扩展代码。值得保留的延伸内容应改写成直接讲解的“补充知识点”，说明它是什么、为什么存在、与本章主链有什么关系。Notebook Cell 本身用于亲手输入、运行和观察，不等于额外作业。

## Notebook 配合规则

Notebook 练习应让学习者逐步获得即时反馈，通常按以下节奏设计：

1. 导入依赖并显示版本；
2. 准备最小配置或测试数据；
3. 创建本章核心对象；
4. 执行一个核心操作；
5. 打印并解释关键结果；
6. 修改一个参数，对比前后差异；
7. 主动触发一个常见错误并记录原因；
8. 用 Markdown 单元格写下自己的总结。

默认让学习者把代码写进模块内自己维护的 `.ipynb`，而不是另建 Python 测试脚本。只有用户明确提出要使用 `.py` 或正式测试框架时，才提供对应文件方案。

不要要求学习者一开始就复制一大段完整代码。文档必须用独立标题明确划分每个 Notebook Cell，变量命名保持连续，并注明前置 Cell 和重启 Kernel 后必须重新运行的 Cell。

Notebook 中不能使用依赖脚本文件位置的 `__file__`。路径应从 `Path.cwd()` 开始，并先打印当前工作目录。异步示例优先使用 Notebook 支持的顶层 `await`，不要默认使用 `asyncio.run()`。

## 根目录 README 同步规则

每次新增学习模块后，都必须检查并按实际情况更新根目录 `README.md`：

- 学习路线中的模块名称、编号、链接和先后顺序；
- “已完成、正在学习、计划中”等状态；
- 后续模块因插入新模块产生的编号变化；
- 当前阶段目标；
- 每日学习计划中受影响的任务。

不要把只有文档规划的内容写成已经实现，也不要为了新增一个模块重写无关路线。

## 重命名与用户文件保护

如果用户要求“只改模块编号或目录名”，执行机械式重命名，不重写原文。验证除明确的路径或编号替换外，内容保持一致。

把工作区中已有或未跟踪的 Notebook、笔记和练习代码视为用户成果。默认保留原样；若确实需要修改，先说明具体文件和必要性。

## 完成交付

最终说明：

- 新增或调整了哪些学习文档；
- 根目录 `README.md` 更新了哪些路线信息；
- 学习者接下来应在 Notebook 中亲手完成什么；
- 哪些代码或答案被有意保留为空；
- 是否读取了参考项目，以及是否对其产生改动。
