# 第 5 章：持久化、启动与增量同步

## 本章目标

理解“数据库文件还在”与“知识文档是否同步”是两个不同问题。

## 1. 重启后发生什么

进程退出后，Python 对象会消失，但 Chroma 文件仍在：

```text
storage/chroma/chroma.sqlite3
```

下次运行 `status` 或 `query` 时，`PersistentClient` 会重新打开这个目录，再按集合名取得已有数据。这个动作不需要重新向量化文档。

## 2. 为什么还需要同步

持久化只说明旧索引还在，不说明它与当前 Markdown 一致。知识库可能发生：

- 新增文件或章节；
- 修改已有内容；
- 删除旧文件；
- 调整切块参数或更换模型。

因此启动流程通常还要决定是否执行同步。

## 3. 本教程的增量同步

运行：

```powershell
uv run python 06-embedding-basics\run.py sync
```

程序比较两组 ID：

```text
current_ids  = 当前 Markdown 重新切块得到的 ID
existing_ids = Chroma 已有 ID

新增 = current_ids - existing_ids
失效 = existing_ids - current_ids
```

处理策略：

- 新增块：调用 Embedding，然后 `upsert`；
- 失效块：按 ID 从 Chroma 删除；
- 未变化块：什么也不做，不再次产生 Embedding 请求。

因此连续运行两次，第二次通常应显示：

```text
added=0, deleted=0
```

## 4. 修改文档后的实验

选择一份练习文档，新增一个独立小节，再运行 `inspect` 检查切块，最后运行 `sync`。

你应观察到：

- 新内容产生新 ID；
- 被修改的旧块 ID 失效并删除；
- 只有新块调用 Embedding；
- 其他未变化文档不重新向量化。

完成实验后恢复文档，再同步一次，索引会再次与文件状态一致。

## 5. WildAgent 的启动方式

WildAgent 当前在创建 `RAGSpecLoader` 时传入 `auto_sync=False`，先让服务完成初始化；如果配置允许，再调用 `start_background_sync()`。

它的目标是：

```text
服务先可用
  +
索引在后台增量补齐
  +
Embedding 慢或超时时不阻塞整个 API 启动
```

教学代码使用前台同步，原因是学习时需要清楚看到每一批何时调用接口。掌握后再看后台线程会更容易。

## 6. 需要特别记住

```text
打开数据库 ≠ 重建数据库
启动服务 ≠ 全量向量化
持久化成功 ≠ 索引一定与当前文档一致
```
