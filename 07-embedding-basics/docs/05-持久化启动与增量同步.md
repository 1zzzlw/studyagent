# 第 5 章：持久化、启动与增量同步

## 本章目标

理解“数据库文件还在”与“知识文档是否同步”是两个不同问题。

## 1. 重启后发生什么

进程退出后，Python 对象会消失，但 Chroma 文件仍在：

```text
storage/chroma/chroma.sqlite3
```

下次运行 `status` 或 `query` 时，`PersistentClient` 会重新打开这个目录，再按集合名取得已有数据。这个动作不需要重新向量化文档。

## 2. 为什么还需要同步

持久化只说明旧索引还在，不说明它与当前 Markdown 一致。知识库可能发生：

- 新增文件或章节；
- 修改已有内容；
- 删除旧文件；
- 调整切块参数或更换模型。

因此启动流程通常还要决定是否执行同步。

## 3. 本教程的增量同步

运行：

```powershell
uv run python 07-embedding-basics\run.py sync
```

程序比较两组 ID：

```text
current_ids  = 当前 Markdown 重新切块得到的 ID
existing_ids = Chroma 已有 ID

新增 = current_ids - existing_ids
失效 = existing_ids - current_ids
```

处理策略：

- 新增块：调用 Embedding，然后 `upsert`；
- 失效块：按 ID 从 Chroma 删除；
- 未变化块：什么也不做，不再次产生 Embedding 请求。

因此连续运行两次，第二次通常应显示：

```text
added=0, deleted=0
```

## 4. 修改文档后的实验

选择一份练习文档，新增一个独立小节，再运行 `inspect` 检查切块，最后运行 `sync`。

你应观察到：

- 新内容产生新 ID；
- 被修改的旧块 ID 失效并删除；
- 只有新块调用 Embedding；
- 其他未变化文档不重新向量化。

完成实验后恢复文档，再同步一次，索引会再次与文件状态一致。

## 5. WildAgent 的启动方式

WildAgent 当前在创建 `RAGSpecLoader` 时传入 `auto_sync=False`，先让服务完成初始化；如果配置允许，再调用 `start_background_sync()`。

它的目标是：

```text
服务先可用
  +
索引在后台增量补齐
  +
Embedding 慢或超时时不阻塞整个 API 启动
```

教学代码使用前台同步，原因是学习时需要清楚看到每一批何时调用接口。掌握后再看后台线程会更容易。

## 6. 需要特别记住

```text
打开数据库 ≠ 重建数据库
启动服务 ≠ 全量向量化
持久化成功 ≠ 索引一定与当前文档一致
```

## 7. Notebook 分单元格练习：观察增量同步

在 `01.basic.ipynb` 中建立 `# 第 5 章：增量同步`。使用 `CountingEmbeddings` 记录收到的文本，证明第二次同步没有重复请求。

### Cell 1：定义计数 Embedding 和 Chunk 工厂

依赖：公共初始化 Cell。

```python
from pathlib import Path
import tempfile

from embedding_lab.chunking import Chunk
from embedding_lab.vector_store import ChromaVectorStore


class CountingEmbeddings:
    def __init__(self):
        self.embedded_texts: list[str] = []

    def embed_documents(self, texts: list[str]) -> list[list[float]]:
        self.embedded_texts.extend(texts)
        return [
            [1.0, 0.0] if "幕墙" in text else [0.0, 1.0]
            for text in texts
        ]

    def embed_query(self, text: str) -> list[float]:
        return self.embed_documents([text])[0]


def make_chunk(chunk_id: str, text: str, source: str) -> Chunk:
    return Chunk(
        id=chunk_id,
        text=text,
        metadata={
            "namespace": "incremental_test",
            "source": source,
            "heading": source,
            "doc_scope": "generation",
        },
    )
```

### Cell 2：创建 Store 和第一版 Chunk

依赖：Cell 1。

```python
persist_dir = Path(tempfile.mkdtemp(prefix="studyagent-incremental-"))
store = ChromaVectorStore(
    persist_dir=persist_dir,
    collection_name="incremental_demo",
    namespace="incremental_test",
    index_signature="teaching-model-v1-chunk-v1",
)
embeddings = CountingEmbeddings()

chunks_v1 = [
    make_chunk("wall-v1", "幕墙需要父墙体", "walls.md"),
    make_chunk("stair-stable", "楼梯连接两个楼层", "stairs.md"),
]
```

### Cell 3：第一次同步

依赖：Cell 2。

```python
first = store.sync(chunks_v1, embeddings)
assert first.added == 2
assert first.deleted == 0
assert len(embeddings.embedded_texts) == 2

print("第一次：", first)
print("累计向量化文本：", embeddings.embedded_texts)
```

### Cell 4：原样同步第二次

依赖：Cell 3。

```python
second = store.sync(chunks_v1, embeddings)
assert second.added == 0
assert second.deleted == 0
assert len(embeddings.embedded_texts) == 2

print("第二次：", second)
```

### Cell 5：修改一个块后再次同步

依赖：Cell 4。

```python
# 模拟墙体正文发生变化：真实 Chunker 会因为 content_hash 变化生成新 ID。
chunks_v2 = [
    make_chunk("wall-v2", "幕墙必须记录 parentWall", "walls.md"),
    make_chunk("stair-stable", "楼梯连接两个楼层", "stairs.md"),
]

third = store.sync(chunks_v2, embeddings)
assert third.added == 1
assert third.deleted == 1
assert len(embeddings.embedded_texts) == 3
assert store.status()["count"] == 2

print("修改后：", third)
print("真正向量化过的文本：", embeddings.embedded_texts)
```

你应该得到下面的关系：

| 同步 | 新增 | 删除 | Embedding 累计文本数 |
|---|---:|---:|---:|
| 第一次 | 2 | 0 | 2 |
| 原样第二次 | 0 | 0 | 2 |
| 修改一个块后 | 1 | 1 | 3 |

### 关键理解

当前教学同步使用稳定 Chunk ID 判断内容是否变化。真实切块 ID 包含 `content_hash`，所以正文改变后会表现为：

```text
旧 ID 失效并删除 + 新 ID 生成向量并写入
```

如果正文变了但 ID 没变，这套简化同步不会自动重新计算向量。这个实验也说明稳定 ID 的生成规则为什么属于索引协议的一部分。
