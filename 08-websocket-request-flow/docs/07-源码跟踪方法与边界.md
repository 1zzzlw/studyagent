# 第7章：源码跟踪方法与边界

## 本章目标

本章结束时，你能使用“调用证据”而不是函数名猜测来跟踪源码，能识别主路径、兼容路径、测试路径和动态节点，并完成08模块的最终调用链记录。

## 前置知识

- 已走通前端协议、WebSocket、GenerationJob、runner、Graph 和事件返回；
- 会使用 `rg` 搜索定义与调用位置；
- 知道测试引用不能自动证明生产主链调用。

## 1. 跟代码时固定问五个问题

每到一个函数，只回答：

1. 谁调用它？
2. 调用发生在启动阶段、请求阶段还是恢复阶段？
3. 输入对象是什么，主关联 ID 是什么？
4. 返回值或副作用是什么？
5. 下一跳的源码证据在哪里？

如果第1问没有答案，先不要继续读函数内部。

## 2. 推荐的 PowerShell 搜索顺序

在 WildAgent 根目录只读执行：

```powershell
rg -n 'msg_type == "user_message"' wild-server/app/api/ws_agent.py
rg -n 'start_job\(' wild-server/app
rg -n 'startup_generation_jobs|_run_persistent_langgraph' wild-server
rg -n 'astream_events\(' wild-server/app
rg -n 'add_node\("classifier"' wild-server/app/agent/graph.py
rg -n 'classifier_node' wild-server/app/agent
```

这个顺序从真实协议分支向下追，不是先打开最大的文件漫无目的阅读。

## 3. 当前源码中的三类路径

### 3.1 当前主路径

```text
agent_websocket.user_message
→ generation_job_service.start_job
→ _spawn / _run_job
→ _run_persistent_langgraph
→ _handle_with_langgraph
→ graph.astream_events
```

### 3.2 兼容路径

`_process_user_message_safely()`、`_handle_user_message()`、`_handle_with_langchain()` 仍在 `ws_agent.py` 中，但当前 WebSocket 接收循环不会从 `user_message` 主分支调用它们。

### 3.3 测试路径

[`test_ws_agent_disconnect.py`](../../../WildAgent/wild-server/tests/network/test_ws_agent_disconnect.py) 会直接调用若干兼容函数验证旧行为和断线边界。测试能证明函数仍被测试，不能证明浏览器真实请求必经它。

判断路径时至少需要一条从生产入口开始的连续调用证据。

## 4. 四种节点定位情况

| 看到的节点名 | 不能直接推断 | 应查看的证据 |
|---|---|---|
| `classifier` | 函数一定也叫 classifier | `add_node("classifier", classifier_node)` 和导入链 |
| `architecture` | 没有额外包装 | `_planned_node("architecture", architecture_planner)` |
| `skeleton` | 一定来自 `skeleton_node.py` | `graph.py` 中 `skeleton_generator` 当前赋值 |
| `door_gen` 等 | 一定有同名 Python 文件 | `gen_name` 生成规则、Component Registry、节点工厂 |

日志和事件给你的通常是“注册名”。注册名、变量名、函数名、文件名可以不同。

## 5. 一次真实请求的观察顺序

启动 WildAgent 后，只选择一条简单 chat 请求，并始终用同一个 `request_id` 过滤：

```text
1. 前端：sendUserMessage 是否发送
2. 后端：agent_websocket 是否收到 type=user_message
3. 任务：start_job 返回 created=True 还是 False
4. runner：是否进入 _run_persistent_langgraph
5. Graph：classifier 的 on_chain_start/on_chain_end
6. 路由：classifier 输出的 intent 是什么
7. 节点：是否进入 chat
8. 出口：是否产生 agent_reply
9. 前端：handleMessage 是否把事件写入正确 session/request
```

不要第一遍就同时打开生成模式、思考模式和计划模式。

### Cell 1：定义源码证据记录

- 依赖：`dataclass`；
- 是否联网：否；
- 预期：每一跳必须记录路径类型和证据。

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class TraceEvidence:
    step: int
    caller: str
    callee: str
    input_object: str
    output_or_effect: str
    source_file: str
    path_kind: str = "primary"


VALID_PATH_KINDS = {"primary", "compatibility", "test", "planned"}
```

### Cell 3：验证证据表不是凭印象填写

- 依赖：Cell 2；
- 是否联网：否；
- 预期：步骤连续、类型合法、证据文件非空。

```python
def validate_trace(rows: list[TraceEvidence]):
    expected_steps = list(range(1, len(rows) + 1))
    actual_steps = [row.step for row in rows]
    if actual_steps != expected_steps:
        raise ValueError("步骤编号不连续")

    for row in rows:
        if row.path_kind not in VALID_PATH_KINDS:
            raise ValueError(f"未知路径类型：{row.path_kind}")
        if not row.source_file.strip():
            raise ValueError(f"第{row.step}步缺少源码证据")
        if not row.caller.strip() or not row.callee.strip():
            raise ValueError(f"第{row.step}步缺少调用关系")


validate_trace(main_trace)
print("主链证据表通过")
```

## 7. 排错顺序

当“前端没有结果”时，不要直接怀疑最后一个节点。依次检查：

```text
WebSocket 是否 OPEN
→ user_message 是否真的 send
→ 后端是否收到并通过协议检查
→ start_job 是新建还是附着旧任务
→ runner 是否已注册并启动
→ classifier 是否 start/end
→ intent 路由到哪里
→ 目标节点是否 end 或抛错
→ 是否产生业务终端事件
→ publish/broadcast 是否成功
→ 前端是否因协议版本或 event_seq 丢弃
→ Store 是否更新正确 session/request
```

每一步只收集事实，不同时修改多个模块。
