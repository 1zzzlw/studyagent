## 1. 完整返回链

```text
_emit_agent_step() / _send_event()
→ versioned_event(payload)
→ sink.send_json(payload)
→ DurableEventSink.send_json()
→ GenerationJobService.publish_event()
→ 按事件类型决定是否持久化
→ _broadcast()
→ 浏览器 ws.onmessage
→ 协议版本检查 + event_seq 去重
→ agentBridge.handleMessage()
→ AgentStore / PresenceStore / Blueprint 加载
```

## 2. 当前前端关注的业务消息

| 消息 | 前端主要效果 |
| --- | --- |
| `generation_resumed` | 恢复请求上下文和 processing 状态 |
| `agent_step` | 更新节点、校验步骤和完成状态 |
| `debug_log` | 保存节点诊断或会话指标 |
| `execution_plan_ready` | 保存最新计划 |
| `execution_plan_review_required` | 显示审核并停止等待动画 |
| `execution_feedback_queued` | 更新排队反馈数量 |
| `thinking_delta/status` | 追加思考或公开进度 |
| `patch_proposal` | 保存场景修改提案 |
| `blueprint_generated` | 下载并加载 Blueprint 产物 |
| `agent_reply` | 写入 Agent 文本回复 |
| `presence_update` | 更新在线用户 |
| `error` | 按错误码恢复 UI 或结束本轮 |

`pong` 和 `network_error` 在进入 `handleMessage()` 前单独处理。

## 3. 哪些事件会持久化

真实 `GenerationJobService` 持久化关键业务事件，例如 `agent_step`、计划事件、`patch_proposal`、`blueprint_generated`、`agent_reply`、`error`。`thinking_delta` 只有 `channel="progress"` 时持久化，原始 reasoning 流不作为恢复历史保存。

原因是：恢复需要重建用户可见结果，但没有必要把每一个高频 token 片段都写入数据库。

## 4. Notebook 分单元格观察

### Cell 1：准备最小前端状态

- 输入：无；
- 依赖：无；
- 预期：得到可观察的状态字典；
- 观察：这是 Python 镜像，不是 Pinia Store 的替代实现。

```python
def new_ui_state() -> dict:
    return {
        "processing": False,
        "steps": {},
        "replies": [],
        "pending_review": None,
        "blueprint_url": None,
        "error": None,
        "online_count": 0,
    }

ui_state = new_ui_state()
ui_state
```

代码解释：把状态集中在一个字典中，便于观察每条事件产生的差异。真实前端会按会话和请求保存更细的状态。

### Cell 2：镜像 `handleMessage()` 的核心分支

- 输入：状态字典和一条事件；
- 依赖：Cell 1；
- 预期：不同 `type` 修改不同字段；
- 观察：协议事件代表“发生了什么”，Store 决定“界面怎样变化”。

```python
def reduce_ui_event(state: dict, message: dict) -> dict:
    next_state = dict(state)
    message_type = message.get("type")

    if message_type == "agent_step":
        steps = dict(next_state["steps"])
        steps[message.get("node", "unknown")] = message.get("status", "running")
        next_state["steps"] = steps
        next_state["processing"] = message.get("stage") != "finished"
    elif message_type == "execution_plan_review_required":
        next_state["pending_review"] = message.get("plan")
        next_state["processing"] = False
    elif message_type == "blueprint_generated":
        next_state["blueprint_url"] = message.get("file_url")
    elif message_type == "agent_reply":
        next_state["replies"] = [*next_state["replies"], message.get("content", "")]
        next_state["processing"] = False
    elif message_type == "presence_update":
        next_state["online_count"] = int(message.get("online_count") or 0)
    elif message_type == "error":
        next_state["error"] = message.get("error", "未知错误")
        next_state["processing"] = False
    return next_state
```

代码解释：函数不修改原状态，而是返回新状态；嵌套的 `steps` 和 `replies` 也创建新对象，避免浅复制后仍共享可变内容。

### Cell 3：播放一组事件

- 输入：开始、完成、回复三条事件；
- 依赖：Cell 1、2；
- 预期：节点完成、processing 为假、回复已保存；
- 观察：事件顺序会影响最终 UI。

```python
event_sequence = [
    {"type": "agent_step", "node": "classifier", "status": "running", "stage": "routing"},
    {"type": "agent_step", "node": "classifier", "status": "done", "stage": "routing"},
    {"type": "agent_reply", "content": "这是回答"},
]

state = new_ui_state()
for event in event_sequence:
    state = reduce_ui_event(state, event)
    print(event["type"], "→", state)

assert state["steps"]["classifier"] == "done"
assert state["replies"] == ["这是回答"]
assert state["processing"] is False
```

代码解释：这类逐事件状态演算能帮助你读 `switch` 中每个 Store 调用，而不用一开始展开整个 Store 文件。

### Cell 4：实现最小事件序号去重

- 输入：同一请求的乱序或重复事件；
- 依赖：无；
- 预期：序号不大于已处理序号的事件被忽略；
- 观察：去重发生在 `handleMessage()` 之前。

```python
def accept_event(last_sequences: dict[str, int], message: dict) -> bool:
    request_id = message.get("request_id")
    event_seq = message.get("event_seq")
    if not isinstance(request_id, str) or not isinstance(event_seq, int):
        return True
    last_seq = last_sequences.get(request_id, 0)
    if event_seq <= last_seq:
        return False
    last_sequences[request_id] = event_seq
    return True

last_sequences = {}
events = [
    {"request_id": "req-1", "event_seq": 1},
    {"request_id": "req-1", "event_seq": 1},
    {"request_id": "req-1", "event_seq": 2},
]
accepted = [item for item in events if accept_event(last_sequences, item)]

assert [item["event_seq"] for item in accepted] == [1, 2]
print(accepted)
```

代码解释：前端真实代码使用 `lastEventSequences` 做同类判断，防止重放事件与实时事件重复更新 UI。

### Cell 5：主动制造未知业务事件

- 输入：当前 reducer 不认识的类型；
- 依赖：Cell 1、2；
- 预期：状态内容不变，但返回的是新字典；
- 排查方向：后端是否新增协议 → TypeScript 联合类型是否更新 → `handleMessage()` 是否新增分支。

```python
before = new_ui_state()
after = reduce_ui_event(before, {"type": "new_server_event", "value": 1})

assert after == before
assert after is not before
print("未知事件没有改变状态")
```

代码解释：真实前端若收到新事件却没有处理分支，通常不会产生预期 UI。协议新增必须同步类型、分发和测试。

## 5. 补充知识点

后端 `versioned_event()` 在事件外层补协议版本；前端先验证版本再分发。这个 Envelope 是所有消息共享的协议外壳，而每种 `type` 的业务字段不同。
