
## 2. 断线恢复不是“从头再生成”

前端连接重新打开后调用 `resumeActiveGenerations()`，发送：

```text
request_id
session_id
last_event_seq
```

后端 `resume_or_replay()`：

1. 按请求或会话查找任务；
2. 重新 `attach()` 当前连接；
3. 先发送 `generation_resumed`；
4. 查询并补发 `event_seq > last_event_seq` 的历史事件；
5. 若任务仍应运行但当前没有活跃 Task，再以 `resume=True` 启动 runner。

历史补发与新的持久事件共用同一把锁，从而保证历史先于新实时事件到达。

## 3. Notebook 分单元格观察

### Cell 1：模拟收到任意服务端消息都证明连接活跃

- 输入：心跳状态；
- 依赖：无；
- 预期：不只 `pong`，普通业务事件也清除等待标记；
- 观察：这是前端真实逻辑的重要细节。

```python
def handle_socket_activity(state: dict) -> dict:
    next_state = dict(state)
    next_state["waiting_for_pong"] = False
    next_state["last_activity"] += 1
    return next_state

heartbeat_state = {"waiting_for_pong": True, "last_activity": 0}
heartbeat_state = handle_socket_activity(heartbeat_state)

assert heartbeat_state == {"waiting_for_pong": False, "last_activity": 1}
print(heartbeat_state)
```

代码解释：只要服务端还能发来合法事件，连接就是活跃的；如果只认 `pong`，长任务产生的正常业务事件仍可能被错误忽略。

### Cell 2：补发断线期间的事件

- 输入：已持久化事件和客户端最后序号；
- 依赖：无；
- 预期：只返回序号2、3；
- 观察：恢复依据是单调事件序号，不是猜测任务执行到哪个节点。

```python
stored_events = [
    {"event_seq": 1, "type": "agent_step", "node": "classifier"},
    {"event_seq": 2, "type": "agent_step", "node": "chat"},
    {"event_seq": 3, "type": "agent_reply", "content": "完成"},
]

def events_after(events: list[dict], after_seq: int) -> list[dict]:
    safe_seq = max(0, int(after_seq))
    return [event for event in events if event["event_seq"] > safe_seq]

replayed = events_after(stored_events, after_seq=1)
assert [event["event_seq"] for event in replayed] == [2, 3]
replayed
```

代码解释：`after_seq` 表示客户端已确认处理到的位置。后端 SQL 也使用 `seq > ? ORDER BY seq` 取得后续事件。

### Cell 3：观察恢复顺序

- 输入：恢复通知、历史事件、新实时事件；
- 依赖：Cell 2；
- 预期：通知最先、历史按序、实时最后；
- 观察：如果顺序颠倒，前端去重可能丢失历史状态。

```python
generation_resumed = {"type": "generation_resumed", "last_event_seq": 3}
new_live_event = {"event_seq": 4, "type": "agent_step", "node": "finished"}
delivery_order = [generation_resumed, *replayed, new_live_event]

assert delivery_order[0]["type"] == "generation_resumed"
assert [item["event_seq"] for item in delivery_order[1:]] == [2, 3, 4]
delivery_order
```

代码解释：星号 `*replayed` 在列表字面量中展开历史列表。真实服务用锁保证补发过程不被新的持久事件插入。

### Cell 4：从多个真实文件自动检查主链锚点

- 输入：`wildagent_root`；
- 依赖：模块 README 的路径 Cell；
- 预期：每个锚点至少找到一次；
- 观察：这是一份可重复的源码验收，不依赖记忆。

```python
source_contract = {
    "wild-web/src/agent/protocol.ts": ["createUserMessageRequest", "AGENT_PROTOCOL_VERSION"],
    "wild-web/src/agent/agentBridge.ts": ["sendUserMessage", "handleMessage", "resumeActiveGenerations"],
    "wild-server/app/api/ws_agent.py": ["agent_websocket", "start_job(", "graph.astream_events("],
    "wild-server/app/services/generation_job_service.py": ["class DurableEventSink", "resume_or_replay", "publish_event"],
    "wild-server/app/agent/graph.py": ["add_node", "set_entry_point"],
}

audit_rows = []
for relative_path, anchors in source_contract.items():
    source = (wildagent_root / relative_path).read_text(encoding="utf-8")
    for anchor in anchors:
        count = source.count(anchor)
        audit_rows.append((relative_path, anchor, count))
        assert count > 0, f"锚点已变化：{relative_path} -> {anchor}"

for row in audit_rows:
    print(row)
```

代码解释：字典把文件映射到锚点列表；嵌套循环逐个检查。结构变化时断言会提醒你重新追踪，而不是继续使用过期路线。

## 6. 补充知识点

- 后台任务恢复依赖任务记录与 Graph Checkpoint；事件重放解决的是前端可见状态，不等于 Graph 状态本身；
- 非持久事件断线期间可能丢失，这是控制存储量与恢复完整度之间的明确取舍；
- 前端指数退避与抖动用于避免大量客户端同时重连，属于可靠性策略，不属于 LangGraph。
