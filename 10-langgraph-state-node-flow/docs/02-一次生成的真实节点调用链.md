# 第02章：一次生成的真实节点调用链

## 本章目标

从真实入口追踪普通生成和 Plan 模式生成。重点是对每一步都回答：谁调用它、它为什么被选择、结束后控制权交给谁。

源码锚点：[graph.py](../../../WildAgent/wild-server/app/agent/graph.py)、[ws_agent.py](../../../WildAgent/wild-server/app/api/ws_agent.py)、[generation_job_service.py](../../../WildAgent/wild-server/app/services/generation_job_service.py)。

## 1. Graph 之外还有运行边界

一次 WebSocket 请求不会直接调用 `architecture_planner()`：

```text
agent_websocket 收到 user_message
→ generation_job_service.start_job(payload, ws)
→ _spawn(job, resume=False)
→ _run_job()
→ self._runner(DurableEventSink, payload, resume)
→ 启动时注入的 _run_persistent_langgraph()
→ _handle_with_langgraph()
→ get_graph(checkpointer=...)
→ graph.astream_events(initial_state, config, version="v2")
→ classifier 节点
```

`GenerationJobService._runner` 是可调用函数，不是事件总线。`DurableEventSink` 提供与 `send_json()` 相容的出口，使运行任务不依赖某一条物理 WebSocket。

## 2. 普通生成分支

`classifier` 返回 `intent="generate"` 且 `plan_mode=False` 时：

```text
classifier
→ architecture
→ material_plan
→ design_review [interrupt]
   ├─ revise  → architecture → material_plan → design_review
   └─ confirm → skeleton
→ Send(component_gen ...)
→ component_val
→ merge
→ final_validate
   ├─ complete/失败不可重试 → END
   └─ partial且仍有预算 → callback → final_validate
```

`Send` 是 `skeleton` 后条件路由函数的返回值。组件数量在运行时才知道，因此无法只靠构图时的固定边表达。

## 3. Plan 模式多了一层调度

`plan_mode=True` 时，分类后先进入：

```text
planning_research
→ [按覆盖情况可选 web_research]
→ planner
→ plan_validator
→ plan_review [interrupt]
→ plan_executor
→ 被批准的业务步骤
→ plan_executor
```

`_planned_node(step_type, node)` 包装业务节点：先执行真实节点，再把 `complete_execution_step(...)` 的计划步骤完成信息合入节点局部返回。

`design_review` 不等于 `plan_review`：

| 审核节点 | 用户看到什么 | 批准后保证什么 |
| --- | --- | --- |
| `plan_review` | 将执行哪些步骤 | Agent 只能按白名单步骤调度 |
| `design_review` | 具体体量、立面、材料与 SVG | 几何从这版设计继续编译 |

## 4. 四种控制流要分清

| 机制 | 示例 | 决策发生时间 |
| --- | --- | --- |
| 固定边 | `component_gen → component_val` | 构图时 |
| 条件边 | `classifier → architecture/chat/patch` | 节点完成后 |
| `Send` | 动态创建若干组件分支 | 路由函数运行时 |
| `Command(resume=...)` | 从审核 interrupt 继续 | 外部输入到达后 |
