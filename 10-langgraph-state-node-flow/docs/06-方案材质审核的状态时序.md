# 第06章：方案、材质、审核的状态时序

## 本章目标

逐字段追踪 `architecture → material_plan → design_review`。这是本次改造真正新增的中间状态主链。

源码锚点：[architecture_node.py](../../../WildAgent/wild-server/app/agent/nodes/architecture_node.py)、[material_plan_node.py](../../../WildAgent/wild-server/app/agent/nodes/material_plan_node.py)、[design_review_node.py](../../../WildAgent/wild-server/app/agent/nodes/design_review_node.py)、[resolver.py](../../../WildAgent/wild-server/app/design/resolver.py)。

## 1. architecture：把候选提升为设计文档

`architecture_planner(state)` 读取：

- `user_message`、`building_type`、`style_preference`；
- `thinking_mode` 和可选 `execution_plan`；
- 上一版 `architecture_plan`、`design_document`；
- `design_feedback`，若是 revise 会进入下一轮设计。

它先生成并归一化候选 `plan`，再调用：

```text
build_design_document(plan, previous=state["design_document"])
→ DesignDocument rN, status=draft
resolve_design(document)
→ ResolvedDesign(design_revision=rN, design_hash=...)
```

局部返回的关键字段：

| 字段 | 值 |
| --- | --- |
| `architecture_plan` | 本轮归一化候选 |
| `design_document` | 可持久化的 draft 文档 |
| `resolved_design` | 确定性派生结果 |
| `design_review_status` | `pending` |
| `design_material_refresh` | 本轮是否需要重算材质 |

若存在旧文档，`build_design_document()` 使用 `old.revision + 1`，同时保留原 `design_id`、`created_at`、锁和未被新规则替换的约束。

## 2. material_plan：更新同一 revision

`material_planner(state)` 读取 `architecture_plan` 和 `design_document`：

1. 若设计修改未涉及材质，复用文档中的 `materials.resolved_plan`；
2. 否则匹配受控资产并生成材质方案；
3. `attach_material_plan(document, plan)` 把材质写回设计；
4. `design_repository.save()` 保存文档并重新解析 `resolved_design`。

材质完善属于同一轮设计内容，因此不会虚增 revision；文档仍回到 `draft`，等待整体审核。

## 3. design_review：第一次执行会暂停

`design_review(state)` 首先运行时：

```python
document = DesignDocument.model_validate(state.get("design_document"))
resolved = resolve_design(document)
decision = interrupt({...})
```

此时函数停在 `interrupt()`，不会执行后面的普通 `return`。Checkpoint 保存的是进入审核时的 State 和待恢复位置。

恢复后节点会从函数开头重新执行，`interrupt()` 返回 `Command(resume=...)` 中的审核决定。

## 4. confirm 与 revise 的字段变化

| 动作 | 文档状态 | 写入 State | 下一节点 |
| --- | --- | --- | --- |
| `confirm` | repository 标为 `approved` | 批准文档、重新 resolve、从文档编译的 `architecture_plan`、材质、`approved` | 普通模式去 skeleton；Plan 模式去 plan_executor |
| `revise` | 保持当前 draft 来源 | 文档、resolve、兼容 plan、材质、`revise`、反馈 | architecture |

revise 之后：

```text
design_feedback
→ architecture 重新生成候选
→ build_design_document(previous=...)
→ revision + 1
→ material_plan
→ design_review 再次暂停
```

## 5. 为什么恢复后要重编译 architecture_plan

用户可能通过设计 API 修改了持久化文档。审核节点优先使用恢复载荷中的文档或 repository 最新文档，然后调用 `architecture_plan_from_document()`。这样旧节点收到的是批准文档的编译结果，而不是审核前遗留在 State 中的旧 plan。

```python
import ast

def literal_return_keys(source: str, function_name: str) -> list[list[str]]:
    tree = ast.parse(source)
    function = next(
        node for node in ast.walk(tree)
        if isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef))
        and node.name == function_name
    )
    groups = []
    for node in ast.walk(function):
        if isinstance(node, ast.Return) and isinstance(node.value, ast.Dict):
            keys = [
                key.value
                for key in node.value.keys
                if isinstance(key, ast.Constant) and isinstance(key.value, str)
            ]
            if keys:
                groups.append(keys)
    return groups

for source_name, function_name in (
    ("architecture", "architecture_planner"),
    ("material", "material_planner"),
    ("design_review", "design_review"),
):
    print(source_name, literal_return_keys(sources[source_name], function_name))
```

## 错误实验

把第一次 `interrupt()` 理解为“返回了一个 decision dict”。检查函数控制流可知，首次运行在这里暂停，后半段还没有执行。只有使用同一 checkpoint 和 `Command(resume=...)` 后，`decision` 才获得恢复值。
