# 三种记忆方案对照实验

三版各自独立实现，不相互导入。原版 `05.chroma.py`、原版 `12-memory/v2`、Generative Agents 和 A-Mem 源项目均不修改。

| 版本 | 记忆架构 | 检索 | 正常对话后的处理 |
| --- | --- | --- | --- |
| v1 | Generative Agents + Ebbinghaus；event / thought / chat、来源证据、衰减强化 | Chroma 语义候选 + GA 近期性、相关性、重要性重排 | 同步强化实际使用的记忆、保存原话、提炼 event；积累达到条件才反思 |
| v2 | **纯 A-Mem**；id / content、关键词、背景、标签、链接、演化历史与访问统计 | 正文语义召回 + links 一跳扩展 | 同步分析新笔记、判断关联与邻居描述演化、保存笔记；不生成 thought，不计算强度 |
| v3 | Generative Agents + A-Mem + Ebbinghaus | GA 重排 + links 与 thought 证据扩展 | 同步强化、保存原话和事件、维护关联；达到条件才反思，新 thought 也维护关联 |

**三版均已删除后台工作队列。** 每一轮都在当前调用中顺序完成，可能等待多次模型请求；完成或报错后才结束本次请求、返回菜单。
网页同时对比三版时，会分别发送三个请求；三个版本可以并行处理，各版本内部仍同步完成整轮。没有排队后自动继续的任务。

## 启动网页

```powershell
cd E:\AgentProject\studyAgent
uv sync
uv run .\12-memory\contrast\web.py
```

浏览器打开 **http://127.0.0.1:80**，保持终端运行。FastAPI 同时提供页面和 API，不需要前端构建、单独的 Chroma 服务或 LangSmith Studio。
不要通过 IDE 的 63342 端口或 `file://` 进行聊天；直接打开 HTML 只能预览样式。

模型配置读取 `studyAgent/.env`，不读取两个参考项目自己的 `.env`：

```dotenv
LLM_MODEL=文字模型名称
LLM_BASE_URL=文字模型接口地址
LLM_API_KEY=文字模型Key
EMBEDDING_MODEL=向量模型名称
EMBEDDING_BASE_URL=向量模型接口地址
EMBEDDING_API_KEY=向量模型Key
```

文字模型与向量模型都通过 LangChain 调用 OpenAI 兼容接口。可选 `LLM_MAX_TOKENS` 默认 8192；`LLM_REASONING_EFFORT` 只在模型支持时配置。

网页功能：

- 三版都从空记忆开始，不自动导入 JSON。顶部选择发给全部还是单版。
- 处理阶段和累计耗时每秒刷新。同一版本同步处理期间，聊天、推进时间和清空操作不能重叠。
- 回答生成后会先写入日志，页面可能先看到回答；发送按钮要等记忆处理完成才恢复。此时显示“同步处理记忆中”，不是后台任务。
- 展开回答可看本轮检索 ID、路径和分数；点 ID 查看完整存储字段。
- v1/v3 显示记忆强度、强化次数、来源、反思认识。v2 只显示真实笔记字段和检索访问次数，不伪造强度或 GA 类型。
- “只问不记”只生成回答和提问日志，不新增记忆、改变访问统计、强化、关联或反思，也不使用 v1/v3 的短期原话。
- “推进时间”把已有记忆时间统一前移。v1/v3 重新计算衰减并清空短期原话；v2 只移动 timestamp 和 last_accessed，没有衰减、到期或遗忘状态。
- “清空”只删除所选版本的 Web 记忆、聊天和时间流逝状态。不存在“等待后台完成”按钮。

模型失败会显示具体错误；已完成的回答与写入保留，不自动回滚、重试或排队。`post_answer_failed` 表示回答后的记忆处理未全部完成，不是模型角色忘记了。

## 记忆结构与执行顺序

### v1：Generative Agents + 衰减强化

```text
用户输入 → Chroma 语义候选 → GA 三因素排序 → 回答
  → 实际采用的记忆强化 → 保存 chat 原话 → 提炼 event
  → 检查新事件积累 → 达到条件则一次归纳 thought → 本轮结束
```

保留 `ConceptNode` 的 event / thought / chat、filling 来源证据、重要性、深度与明确纠正关系。
反思每轮只做本地检查，满足条件后一次调用文字模型，不再额外生成焦点问题或逐题向量检索：

- 本轮必须有新事件，积累至少两次不同观察的事件。
- 默认积累至少 3 条未处理事件；或至少 2 条且重要性合计达到 15。
- 种子记忆、原话 chat 和已有 thought 不增加触发量，最多提供 12 条证据资料。
- 模型使用 M1、M2 等临时引用号，程序映射成真实 ID 写入 filling，不让模型抄长 ID 或混用来源 ID。
- 每条认识至少两个不同的有效引用，且至少一个是待反思新事件。引用错误只跳过这一条，保留其他有效认识，不额外调用模型重试。
- 无引用错误时，把这批事件标记为已参与反思；空 thoughts 也是一次正常检查。有引用错误则保留待处理标记，等以后出现新事件再尝试。
- 不强制生成认识；姓名、饮料、面试等无关事实本身不需要硬凑出联系。

阈值在 v1/v3 各自的 reflection.py 顶部。它们是实验规则，不是认知心理学定律。
新认识至少引用两条不同的真实证据。
不建立 A-Mem 的 context / tags / links。

### v2：纯 A-Mem

```text
用户输入 → 正文向量召回 → links 一跳扩展 → 回答
  → 登记已检索笔记的访问统计 → analyze_content
  → process_memory：查询邻居、决定建立链接或更新邻居 context/tags
  → 向量化并保存用户原文笔记 → 本轮结束
```

字段沿用本地 A-Mem 的 `MemoryNote`：

```text
id, content, keywords, context, tags, category, links,
timestamp, last_accessed, retrieval_count, evolution_history
```

- 不含 GA 的 type、subject/predicate/object、filling、poignancy、depth、thought、反思或纠正淘汰逻辑。
- 不含 Ebbinghaus 引擎、initial_strength、stability_days、成功回忆强化或遗忘状态。
- 一条用户消息保存为一条原文笔记；AI 回答只进聊天日志，不另外保存为用户经历。不使用 v1/v3 的短期原话窗口。
- `retrieval_count` 记录正常提问时笔记进入回答上下文的次数，包括没有被回答最终引用的候选；它不影响排序或回答清晰程度。只读提问不计数。
- `strengthen` 是 A-Mem 演化动作名，表示建立语义 links，不是提高用户引擎的强度。
- 新笔记可以指向已有笔记；不强制补反向边。邻居 context/tags 更新会持久化，正文不因语义演化而改写。
- 与本地参考实现相比，用真实 ID 更新邻居、保存演化历史，并为一跳邻居预留最多三个上下文位置，避免原代码邻居被最终截断的问题。
- 时间使用带时区的 ISO 格式，字段名保持 timestamp / last_accessed。查询只向量化 content；语义 metadata 更新不重新向量化。

这里复现 A-Mem 的记忆架构和主要流程，使用本项目的 LangChain、Chroma 持久化和聊天界面作为应用接入。

### v3：三者结合

```text
用户输入 → Chroma 语义候选 → GA 排序 → 扩展语义 links / thought 证据 → 回答
  → 实际回忆强化 → chat / event 写入 → 关联维护
  → 检查新事件积累 → 达到条件则一次归纳 thought → 新 thought 关联维护 → 本轮结束
```

`filling` 保存来源证据，`links` 保存语义关联，`supersedes_id` 保存明确纠正关系。它们不是同一种关系。

v1/v3 的 GA 排序为 `0.5×近期性 + 3×相关性 + 2×重要性`，三个分量分别归一化。
近期性按访问顺序的 `0.99^rank` 计算，不是 Ebbinghaus 按天衰减的清晰度。
记忆强度只影响提示词中的回答清晰程度，不混入检索分数；forgotten 也不会仅因为强度低就被排除。
当前仍提供入选记忆正文，所以低强度并不保证模型一定答不出细节。

## 手机页面与记忆关联图

顶部导航进入独立的“记忆关联图”，支持单版 / 三版查看、拖动缩放、搜索 ID 或正文、查看直接关联和完整字段。

- v1/v3 显示 chat / event / thought；来源证据和纠正保留箭头，v3 双向语义链接合并显示。
- v2 全部是 note，按实际 links 方向画箭头；分列只是布局，不代表三种分类。详情保留全部笔记字段和演化历史。
- 图每三秒只读刷新，不调用模型，也不改变访问次数或强化；不按强度、数量隐藏记忆。
- 手机通过标签切换回答，完整记忆列表和处理进度在聊天区域下方。

## 自己聊天的对照问题与预期

建议从空库开始，把相同消息发给三版。每轮等发送按钮恢复后继续；探测问题可开启“只问不记”。

| 步骤 | 输入消息 | 观察和预期 |
| --- | --- | --- |
| 1 | 我叫林舟，平时喜欢喝乌龙茶，晚上不喝咖啡。 | v1/v3 可提炼事件；v2 保存原文 note，生成 keywords/context/tags。第一次没有旧邻居，可以没有链接。 |
| 2 | 昨晚我喝了咖啡，结果到凌晨两点还没睡着。 | 查看新增记忆、v2/v3 是否建立相关 links；不要把单次经历归纳成确定因果。 |
| 3 | 今天我看书时很难集中注意力，可能是昨晚没睡好。 | v1/v3 达到积累条件才调用反思模型，可能新增带证据的 thought；v2 更新笔记关联或背景，没有 thought。 |
| 4，只读 | 晚上帮我选一杯饮品吧，你会怎么选？ | 检查乌龙茶、不喝咖啡的事实是否进入上下文。答对只是一次结果，不能单凭语气判断架构。 |
| 5，只读 | 结合最近这些事，你对我的作息有什么认识？ | v1/v3 可使用已保存 thought；v2 也能即时推理，但不会把该回答存为独立反思认识。 |
| 6 | 我同学叫陈橙，她喜欢咖啡，这说的是她，不是我。 | 看关联维护是否错误合并人物，回答“谁喜欢咖啡”时核对正文和实际检索 ID。 |
| 7 | 明天如果你有空，我们下午两点去东门见面吧，记得带我借给你的《活着》。 | 保存邀请、时间条件与借还方向，不当作已经确认、已经完成。 |
| 8，只读 | 那本书我已经拿回来了吗？ | 没有完成证据，应说明不知道，不能因为问句预设就承认归还完成。 |
| 9，推进90天后只读 | 你还记得我平时喜欢喝什么吗？ | v1/v3 同一记忆强度应降低，表达可能变模糊；v2 没有强度衰减，不能要求它表现遗忘。 |

事实变化也可单独测试：先说“我现在住城北”，后说“我上个月搬到了城南”，再问现在 / 以前住哪。
v1/v3 保留事件和来源；v2 保留两条原文笔记及其语义背景。当前并没有为纯 A-Mem 添加 GA 式事实作废机制，检索或模型可能混淆，正是要观察的差异。

关联更多、thought 更多、回答更长不代表效果更好。重点记录事实准确性、人物或时间混淆、编造、关联是否有用，以及实际引用了哪些记忆。
三种整套方案的结构、短期窗口和回答上下文不同，不是单变量消融实验，也不预设 v3 最好。

## 终端入口

```powershell
.\.venv\Scripts\python.exe .\12-memory\contrast\v1\main.py
.\.venv\Scripts\python.exe .\12-memory\contrast\v2\main.py
.\.venv\Scripts\python.exe .\12-memory\contrast\v3\main.py
```

三条命令按需分别运行。终端直接使用 input / print，处理期间会阻塞，不再使用后台输入重绘器。

- v1/v3 CLI 沿用原先的 300 条基线导入、`--import-only` 和菜单“恢复300条”；首次导入只调用向量模型。网页仍不读取基线。
- v2 CLI 与网页一样从空笔记开始，没有种子导入、衰减字段或恢复300条入口；菜单 5 清空笔记。
- 三版都保留 `--question "你的问题"` 只读提问、时间流逝、统计和退出菜单；不再有等待后台的菜单 6。
- CLI 固定实验时间默认 `2026-11-10T12:00:00+08:00`，可在全新实验配置 `EXPERIMENT_NOW`。网页首次保存共同时间到 clock.json，重启沿用。

## 代码与数据位置

| 代码 | 作用 |
| --- | --- |
| 各版 models.py | 记忆结构和模型输出格式；v2 只有 A-Mem 笔记 |
| 各版 store.py、strategy.py | 独立 Chroma 存储和检索 |
| 各版 runtime.py、llm.py | 同步整轮处理和真实 LangChain 模型接入 |
| v1/v3 engine.py、reflection.py | 衰减强化与带证据的反思 |
| v2/v3 association.py | A-Mem 语义分析、关联与邻居维护 |
| web.py、web_service.py、static/ | FastAPI、界面适配、聊天页和关联图 |

三版 Web 数据仍在 `storge/web/chromadb/v1|v2|v3` 与 `storge/web/v1|v2|v3`，没有新建迁移存档。
你已删除旧聊天数据，本次从空库使用新结构。v2 不兼容旧混合版 payload；若某个环境还有旧 v2 集合，需先清空该环境 v2 存档再启动，程序不会自动混读或删除。
CLI 使用 `storge/chromadb/版本` 和 `storge/版本`，与网页独立。

`results.jsonl` 保存问题、回答、实际使用 ID、候选路径和分数、模型上下文、模型名与处理阶段。
正常对话先记录 `dialogue_processing`，成功后 `dialogue_complete`；失败记录 `post_answer_failed` 和错误详情。只读为 `read_only_complete`。
v1/v3 的每轮结果新增 reflection：触发状态、跳过原因、积累量、临时号到真实 ID 的映射、模型结构化输出、已保存认识和逐条拒绝原因。网页回答下可展开查看。
未触发反思时没有反思模型调用；正常触发只有一次，v3 新认识的关联维护仍可能另调模型，因此不保证三版耗时一样。
同一 turn_id 的末条记录表示该轮当前结果。v2 候选字段是 id，上下文是“记忆笔记”；v1/v3 是 node_id 和“长期记忆”。
