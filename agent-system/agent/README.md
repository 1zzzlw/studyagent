> 四系统初版现已实现。启动、实际目录、存储和测试入口见 [运行说明](../README.md)。本文保留早期职责与细分目录规划；没有同名源文件的条目仍是后续规划，不要求初版逐一拆分。

> 后端编辑区域：`E:\AgentProject\studyAgent\agent-system`；Flutter 测试前端在 `E:\FlutterProject\ai_app`。Generative Agents、A-Mem、Sentimo 仅供阅读和借鉴。已有 `.env` 保留。

## 1. 这次要构建什么

以四个并列的业务系统组织代码：

| 系统 | 主要问题 | 负责输出 |
| --- | --- | --- |
| 记忆系统 `memory` | 经历过什么？有哪些关联和新认识？现在记得多清楚？ | 相关记忆、本轮回忆视图、记忆更新 |
| 人物状态系统 `character_state` | 角色现在处于什么处境？能投入多少精力与注意力？ | 当前状态快照、本次注意力评价 |
| 情感系统 `emotion` | 这次交流让角色产生什么感受？情绪如何延续和恢复？ | 当前情绪快照、本次情感评价 |
| 对话系统 `dialogue` | 基于以上信息，此刻怎样表达？ | 一次回复及所采用的记忆 ID |

“四系统”描述业务职责，不表示每条消息必须依次经过四层继承关系。

外面的应用编排负责调用顺序，技术基础设施负责模型与存储。它们是支撑代码，不增加新的业务系统。

## 3. 每个系统内部怎样分层

| 内部层 | 职责 | 示例 |
| --- | --- | --- |
| `domain` | 定义属于本系统的数据及语义 | 记忆节点、人物状态、情绪向量 |
| `application` | 完成一个具体业务动作，协调数据和引擎 | 生成反思、维护关联、更新情绪 |
| `engines` | 执行可单独理解的规则或算法 | 记忆衰减、情绪混合、注意力评价 |
| `ports` | 说明服务需要怎样的外部能力 | 记忆仓库、向量检索；先在记忆系统定义必要接口 |
| `prompting` | 将输入组织为模型能理解的内容 | 对话提示词构建 |

并非每个系统都需要所有内部层。对话系统无需单独计算情绪或管理长期记忆。

推荐依赖方向：

~~~text
应用编排
    ↓ 调用公开服务
各系统 application
    ↓ 使用
本系统 domain / engines / 必要的 ports

基础设施实现存储、模型等外部能力，由初始化入口传入服务。
~~~

系统之间通过明确输入和快照交互。情感系统不会直接修改记忆仓库，对话系统不会直接修改人物状态。

## 4. 字段归属

| 字段或概念 | 放在哪里 | 如何传递 |
| --- | --- | --- |
| 精力 `energy`、活动、环境、忙碌程度、注意力焦点 | 人物状态系统 | 提供本轮状态快照 |
| `attention` | 人物状态系统的 `AttentionAppraisal` | 评价本次观察，用于选择记忆细节与初始化强度 |
| 当前喜悦、悲伤、愤怒、恐惧、信任感、好奇 | 情感系统的 `EmotionState` | 直接影响对话，也参与本次反应评价 |
| `emotional_impact` | 情感系统的 `EmotionAppraisal` | 表达本次观察对角色的冲击程度 |
| 记忆重要性 `importance` | 记忆形成的评价结果 | 参与长期保留决策及初始强度计算 |
| 正文、来源、证据、普通关联 | 记忆系统 | 保存可追溯的经历和认识 |
| 初始强度、稳定性、实际回忆次数、强化基准 | 记忆系统的 `RetentionState` | 引擎据此计算当前强度 |
| 关联是否已处理、待反思事件等 | 记忆系统的处理进度 | 与记忆正文结构分开管理 |
| 本轮已采用的记忆 ID | 对话输出 | 编排交回记忆系统登记回忆 |
| 用户与角色的实际发言 | 原始对话记录，由编排保存 | 记忆通过消息 ID 追溯原话 |

记忆正文不再保存“当前精力”“当前情绪”，也不必永久保存 `attention`、`emotional_impact`。

如以后需要追溯初始化原因，可把形成时的评价记录放进独立处理日志。它是一份历史评价，不随当前状态变化而改写。

## 5. 系统怎样互相影响

~~~mermaid
flowchart TD
    U["用户消息 / 显式环境事件"] --> S["人物状态系统"]
    U --> E["情感系统"]
    U --> M["记忆系统"]
    S -->|"本次注意力、当前处境"| M
    E -->|"本次情感反应"| M
    M -->|"相关经历，供本轮评价"| E
    E -->|"本轮状态变化建议"| S
    S -->|"精力、活动、注意力"| D["对话系统"]
    E -->|"当前感受与表达倾向"| D
    M -->|"相关内容与本轮清晰程度"| D
    D -->|"实际回复、采用的记忆 ID"| A["应用编排"]
    A -->|"保存交流，触发记忆整理与强化"| M
~~~

箭头是影响关系；执行时不让系统无限互相调用。第一版由应用编排控制每轮各步骤的执行次数。

具体顺序见 [应用编排](application/README.md)。

## 6. 四个关键设计决定

### 6.1 情绪和状态直接影响对话

它们既可以影响记忆形成，也向对话提供独立信息。

记忆强度表示本次回忆清晰程度；它无法代替情绪类型、疲惫程度或当前活动。

### 6.2 记忆保留两种不同的联系

- `evidence_memory_ids`：这条认识根据哪些记忆形成，有方向。
- `related_memory_ids`：哪些记忆相关，第一版按普通双向关联处理。
- `source_message_ids`：原始交流证据，引用消息而非其他记忆。

借鉴 GA 的反思与来源记录，借鉴 A-Mem 的语义描述、普通关联和邻居维护，但不继续用含义随类型变化的 `filling` 混装所有内容。

### 6.3 强度影响回忆视图，原始内容保留

正文与生命周期数据分开保存。引擎计算当前强度后，生成 `RecallItem` 等本轮视图提供给对话。

第一版可以把正文、清晰程度和表达约束一起交给回复模型。低强度不等于事实错误，也不自动允许改写事实。若后续要做到实际省略细节，再单独完善回忆整理策略。

### 6.4 对话系统只做一次回复调用

一次 `DialogueService.generate(...)` 组织提示词后，只调用一次回复模型。

情感评价、记忆形成、反思、关联维护可能各自使用模型，因此“一次交流”不保证总共只有一次模型请求。调用次数按系统分别记录。

初版采用清晰的同步编排；回复产生后再顺序整理记忆。后台队列与并发调度可在实际需要时另行设计。

## 7. 三个参考项目分别借鉴什么

| 来源 | 参考位置 | 本框架采用的职责 |
| --- | --- | --- |
| Generative Agents | [associative_memory.py](../../../generative_agents/reverie/backend_server/persona/memory_structures/associative_memory.py) | `event / thought / chat` 类型、来源、反思层级 |
| Generative Agents | [reflect.py](../../../generative_agents/reverie/backend_server/persona/cognitive_modules/reflect.py) | 从已有经历生成新认识，并记录真实证据 ID |
| A-Mem | [memory_system.py](../../A-mem/agentic_memory/memory_system.py) | 关键词、context、tags、普通关联及邻居描述维护 |
| Sentimo | [state.py](../../sentimo/src/state.py) | 人格调节、情绪向量、平滑更新、向基线恢复 |
| Sentimo | [cli.py](../../sentimo/src/cli.py) | 将当前情绪与人格参数直接组织进回复提示词 |
| 现有记忆 Demo | [v3/engine.py](../../12-memory/contrast/v3/engine.py) | 可替换的 Ebbinghaus 衰减强化引擎 |

需要明确的区别：

- Sentimo 没有完整实现你设想的“精力、活动、环境、忙碌程度”系统；这些字段与规则需要结合你的已有设计补充。
- Sentimo 的情绪分类偏向识别消息情绪，本项目需要评价“角色读到这些内容后的反应”。不能直接把用户悲伤等同于角色必然悲伤。
- Sentimo 当前的基线恢复是按处理消息迭代的规则。要支持真实时间或模拟时间推进，需要在后续实现中明确转换。
- 人格调节参数先作为角色初始化配置，不在本轮新增独立的人格系统。情绪中的 `trust` 暂表示当前信任感，不等同于完整人物关系模型。
- 不直接导入或运行参考仓库中的业务类；参考后在本目录实现，避免跨仓库耦合。

## 8. 存储规划

| 数据 | 初版计划 |
| --- | --- |
| 完整历史对话 | SQLite，按角色、会话保存实际消息；见上级目录 init.sql |
| 短期记忆 | 从历史读取最近 N 条，在内存组织滑动窗口；后续结合 token 预算 |
| 长期记忆正文及证据、关联 | SQLite 主数据与独立关系表，初版已实现 |
| 记忆生命周期与处理进度 | 独立 SQLite 表，通过记忆 ID 关联，初版已实现 |
| 人物状态、情绪 | 分别保存角色快照 |
| 向量索引 | 沿用现有 Chroma 依赖；只负责候选检索与 ID，不承担所有领域状态 |
| 模型配置 | 初始化时读取上级目录已有 `.env`，由统一模型适配器使用 |

三层是数据职责的划分，不要求三套独立数据库。短期窗口滑出不删除历史，也不代表自动形成长期记忆。

实际沿用上级目录已创建的 `storge/sqllite` 和 `storge/chromadb`，启动会初始化数据库，不导入示例聊天或记忆。详细说明、字段与窗口查询见 [三层记忆与历史数据库](infrastructure/persistence/README.md)。

## 9. 后续实现顺序

1. 实现公共消息与时间、四系统最小数据模型。
2. 实现状态快照与情绪引擎，先能观察独立变化。
3. 实现一次回复调用，接入状态和情绪快照。
4. 接入原始对话存储、记忆形成与按 ID 读取。
5. 接入向量候选检索、回忆视图、实际回忆后的强化。
6. 接入 GA 反思和 A-Mem 普通关联，设置触发条件并保留证据。
7. 通过连续交流观察系统之间的影响，再决定参数和额外机制。
