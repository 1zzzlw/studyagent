# 回复协调层

借鉴 MaiBot 私聊的三段分工：消息触发 → Planner 决策 → Replyer 发言。这里不移植群聊门控、多聊天 Focus、插件和工具发现。

参考源文件（仅只读）：

- `MaiBot/src/chat/debounce/README.md`：natural 档固定防抖，安静/活跃开批、续发和整批上限。
- `MaiBot/src/maisaka/turn_trigger/scheduler.py`：先收齐消息，再决定进入 Planner。
- `MaiBot/src/maisaka/scenes/private/scheduling.py`：私聊新消息结束等待，重新判断。
- `MaiBot/prompts/zh-CN/maisaka_chat.prompt`、`builtin_tool/wait.py`：Planner 选择 reply、wait 或结束本轮，不自己输出聊天正文。

## 本目录

`coordinator.py` 负责即时接收、单调时钟防抖、唤醒与版本检查。每个会话单独记录输入版本；一个角色工作线程串行执行模型和记忆操作。`planner.py` 用一次结构化模型调用返回 action、reason、wait_seconds 和 reply_reference，后者是指导而非正文。

POST 消息返回 202，表示已保存并接收，不代表已经完成回复。前端每秒请求当前会话的 activity，再读取新历史；界面不再因模型仍在生成而禁止续发。

## 三种决策

| action | 行为 |
| --- | --- |
| reply | 检索、评价、生成回复；确认本批仍有效后发布，再整理记忆 |
| wait | 不发言且暂不整理本批；新消息或指定时间到期后继续判断 |
| skip | 不生成 assistant 消息，仍评价状态并整理真实观察 |

wait_seconds=null 表示只等待新消息。同一批最多自动超时复判一次，继续等待时停在消息唤醒状态，不无限重复请求同一份输入。

## 连发与过时结果

1. 每条原话立即保存，各有独立消息 ID，不把用户几条消息篡改成一条历史。
2. 收齐当前批后传入 Planner；本批后续阶段采用同一个输入版本。
3. 每次模型调用结束后检查版本。出现同会话的新输入，旧批尚未发布的结果被丢弃。
4. 发布前的版本检查与提交、接收新消息共用互斥区，防止检查通过后又夹入一条新消息。
5. 候选情绪在发布前不修改真实状态；实际发布后才强化采用的记忆，避免失效批次影响人物。
6. 已发布的回复继续完成记忆整理，新一批排在后面；远端同步调用不能保证立即取消。

重启时不自动重放未完成调用，原话保留，未完成轮次标记失败/部分完成。变化记录包含 Planner 上下文、决策、等待、丢弃和记忆处理过程；不记录隐藏推理。

## 手动验证

先快速分三条发“我想跟你说一件事”“是今天项目的事”“我终于把它跑起来了”，观察只形成一次统一回复。再试“等一下，我还没说完”，待 Planner 进入等待后补充“说完了，现在可以回了”。最后试“这个只是告诉你，不用回答”，查看 Planner 是否选择 skip，并检查 messages 中没有伪造的 assistant 消息。

模型的语义决策不保证固定句式必选某一动作，实际理由以 planner_decision 事件为准。
