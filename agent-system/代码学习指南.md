# agent-system 代码学习指南

这份文档帮助你第一次阅读当前实现：先知道代码最终完成了什么，再沿着一次交流找到各系统的职责，最后理解关键计算和存储方式。阅读重点是人物状态、情感、记忆，以及把它们串起来的对话和应用编排。

本文根据当前源码整理。架构图表示整体目标，下面介绍已经落地的行为；示例中的语义提炼只是帮助理解，不代表真实模型一定生成相同结果。启动与部署细节见 [README](README.md)。

## 1. 读完以后，你应该能回答什么

先用这几个问题确定阅读目的：

1. 用户发出一句话后，哪些代码先执行，哪些代码后执行？
2. 人物状态、情绪、注意力、记忆重要性分别由谁产生？
3. 一段原话怎样变成事件，再怎样变成反思认识？
4. 已检索的记忆为什么不一定会被强化？
5. 推进时间之后，什么变了，什么仍然保留？
6. 到哪里查看某轮模型输入、输出、情绪变化和记忆来源？

第一遍不需要记住所有字段和 SQL。能沿着 `Runtime.process_pending()` 解释一批消息的流向，就已经掌握了主体。

## 2. 从你的架构图定位当前代码

| 图中的系统 | 当前实现位置 | 当前做到哪里 |
| --- | --- | --- |
| 人物状态 | [character_state](agent/systems/character_state/) | 状态快照、手动更新、本轮注意力计算 |
| 情感 | [emotion](agent/systems/emotion/) | 角色反应评价、六维情绪混合、随时间恢复 |
| 记忆 | [memory](agent/systems/memory/) | 事件形成、关联、检索、衰减、强化、反思和来源追溯 |
| 认知与反思 | [MemoryService.reflect](agent/systems/memory/application/service.py) | 从多条事件归纳 thought；尚未独立成完整认知系统 |
| 对话 | [dialogue](agent/systems/dialogue/) | 汇总上下文，生成回复并报告采用的长期记忆 |
| 人格与身份 | [情绪参数](agent/systems/emotion/engines/dynamics.py) 与 [对话提示词](agent/systems/dialogue/prompting/builder.py) | 固定调节参数和角色表达约定，尚未独立成系统 |
| 人物关系 | 尚无独立业务模块 | 情绪里的 trust 表示当前信任感，尚未建立面向不同对象的关系模型 |
| 目标与行动 | 尚无独立业务模块 | 状态中有 current_intent；Planner 负责聊天发言决策，尚未实现长期目标和行动执行 |

当前实现有四个业务系统：人物状态、情感、记忆、对话。外面的回复协调层和 Runtime 负责安排执行顺序。

图中的双向影响不会在代码里变成无限互相调用。例如记忆影响情绪，情绪又影响新记忆，但它们在一次处理中各自有明确执行位置。

## 4. 先跟着一批消息走一遍

假设你连续发出两条消息：

> 我最近总去图书馆。  
> 三楼靠窗那里安静，比较容易看进去。

### 4.1 接口先接收，不等模型完成

入口是 [api.py](agent/api.py) 的 `send()`：

```text
POST /api/conversations/{key}/messages
    → ReplyCoordinator.submit()
    → Repository.begin_turn()
    → 保存用户原话和处理记录
    → 返回 HTTP 202
```

每条用户消息都有自己的 `message_id` 和 turn 记录。这里的 turn 是处理记录；连续多条消息可以组成一批，共用一次回复。

同一消息 ID 重发相同正文，会返回已有处理结果；如果同一 ID 对应不同正文或不同会话，会报错，避免重复接收造成重复处理。

### 4.2 协调层收集连续消息

[coordinator.py](agent/application/reply_control/coordinator.py) 中的 `ConversationSchedule.receive()` 设置等待截止时间。默认规则是：

- 安静一段时间后开批，等待 2 秒。
- 距离上一条消息不超过 30 秒时再次开批，等待 5 秒。
- 同批续发通常重新等待 2 秒，但收集阶段最多延长到本批开始后 8 秒。

这些时间用于收集输入，模型处理耗时另算。一个工作线程串行执行实际处理。

### 4.3 Runtime 组织本轮上下文

主线在 [runtime.py](agent/application/runtime.py) 的 `process_pending()`：

1. 读取人物状态和随时间恢复后的情绪快照。
2. 读取本批输入之前、当前会话最近 12 条消息，按总共 12000 字符限制窗口。
3. 把本批用户消息单独放进上下文，保留各自的 ID 和时间。
4. 加入角色名、当前北京时间等信息。
5. 调用 Planner。

这里的 12000 是字符预算，不是 Token 预算；本批输入单独加入，也不包含在这个近期窗口预算内。

### 4.4 Planner 决定是否发言

[planner.py](agent/application/reply_control/planner.py) 通过模型生成 `ReplyDecision`：

| action | 后续行为 |
| --- | --- |
| reply | 检索、评价情绪、计算注意力、生成回复、整理记忆 |
| wait | 本次返回等待决定，暂不执行后面的情绪评价和记忆整理 |
| skip | 不生成回复，仍检索、评价情绪并整理记忆 |

`reply_reference` 是交给回复模型的方向提示，具体正文由对话系统生成。

等待可以由新消息提前唤醒。同一批最多进行一次定时超时复判，之后仍想等待就停下来等新消息，避免无人聊天时反复调用模型。

### 4.5 检索 → 情感评价 → 注意力 → 回复

当决定为 reply 或 skip 时，Runtime 按这个顺序执行：

```text
MemoryService.recall()
    → 找出本轮相关长期记忆
EmotionService.appraise()
    → 结合状态、原有情绪和记忆，算出本轮情绪候选
CharacterStateService.appraise()
    → 根据人物状态和候选情绪计算注意力
DialogueService.generate()          仅 reply 分支执行
    → 生成 answer 和 used_memory_ids
```

情绪评价发生在回复之前，因此本轮新情绪可以直接影响回复语气。注意力也会用于后续形成记忆；当前回复上下文包含人物状态，但没有单独加入本轮 `AttentionAppraisal` 对象。

### 4.6 先确认仍然有效，再提交

连续消息可能在模型生成过程中到达。协调层用 `revision` 记录当前会话的输入版本：新消息让版本增加。

旧批次模型请求可能仍会完成，但如果版本已经变化，其候选情绪和正文不会提交，也不会依据该正文强化记忆。

`commit_if_current()` 把版本检查和提交放在协调层同一把锁内。通过检查后，才保存真实情绪和 assistant 消息。

这也解释了 `EmotionService.appraise()` 为什么返回 `appraisal, before, after`：先给出计算结果，真正保存由 Runtime 决定。

### 4.7 回复提交后，再整理记忆

```text
提交真实情绪和回复
    → record_usage()：强化回复中实际采用的旧记忆
    → remember()：保存 chat、提炼 event、维护关联和索引
    → reflect()：符合条件时生成 thought
    → 完成这一批的处理记录
```

回复可能已经显示，记忆整理仍在运行。如果后续失败，处理状态可以是 partial，已保存的回复继续保留。

正常 reply 分支有四次文字模型调用：Planner、情绪评价、对话、记忆形成。触发反思时再增加一次。向量接口请求另算，规则计算本身不调用模型。

## 5. 人物状态系统：角色此刻能投入多少注意力

先读 [domain/models.py](agent/systems/character_state/domain/models.py)，再读 [application/service.py](agent/systems/character_state/application/service.py)，最后看 [engines/attention.py](agent/systems/character_state/engines/attention.py)。

### 5.1 状态字段

| 字段 | 含义 | 默认值 |
| --- | --- | --- |
| energy | 精力，0～1 | 0.7 |
| busyness | 忙碌程度，0～1 | 0.1 |
| activity | 当前活动 | 休息时聊天 |
| attention_focus | 注意力焦点 | 当前对话 |
| environment | 所处环境 | 安静的房间 |
| current_intent | 当前意图 | 理解对方并自然交流 |
| updated_at | 状态更新时间 | 保存时传入 |

`CharacterState` 是角色的状态。用户说“我累了”不会直接把角色的 energy 改低。当前状态由显式操作更新，没有自动作息或精力消耗模拟。

### 5.2 注意力怎样算

`evaluate_attention()` 的规则可以写成：

```text
distraction = 0.2 × fear + 0.15 × sadness
attention = (0.3 + 0.7 × energy)
            × (1 - 0.6 × busyness)
            × (1 - distraction)
最终限制在 0.05～1.0，并保留三位小数
```

精力越低、越忙、越担忧或悲伤，本轮注意力越低。activity、environment 等文字字段会进入模型上下文，但不直接参与这个数值公式。

输出 `AttentionAppraisal` 包含注意力数值和简短依据。这个输出属于本轮评价，没有直接写回 CharacterState。

## 6. 情感系统：角色怎样产生反应并恢复

阅读顺序：[数据模型](agent/systems/emotion/domain/models.py) → [服务](agent/systems/emotion/application/service.py) → [计算规则](agent/systems/emotion/engines/dynamics.py)。

### 6.1 区分三个概念

| 对象或字段 | 意义 |
| --- | --- |
| EmotionState | 角色当前情绪，包括六维数值、恢复基线和更新时间 |
| EmotionAppraisal.reaction | 模型评价出的本次目标情绪，是混合计算的输入 |
| EmotionAppraisal.emotional_impact | 本次内容对角色的冲击程度，传给记忆系统 |

六个维度是 joy、sadness、anger、fear、trust、curiosity，分别限制在 0～1。它们独立取值，不要求加起来等于 1。初始各维度默认 0.15，恢复基线默认 0.1。

“当前悲伤很高”和“本次内容冲击很大”是不同信息：悲伤可能是之前留下的，新消息也可能带来很强的喜悦冲击。

### 6.2 模型负责评价什么

`EmotionService.appraise()` 把角色当前处境、固定人格参数、原有情绪、相关经历和用户原话交给模型。

模型返回 `reaction`、`emotional_impact`、`reason`。这里评价的是角色自身读到消息后的反应，而不是识别用户情绪后原样复制。

### 6.3 规则负责怎样变化

`recover()` 按距离快照更新时间的小时数恢复情绪：

```text
factor = exp(-流逝小时数 / 6)
恢复后数值 = baseline + (原数值 - baseline) × factor
```

6 小时是指数恢复的时间尺度。6 小时后与基线的差距约为原来的 36.8%，并非已经完全恢复。

`apply()` 先恢复旧情绪，再用固定人格参数计算混合系数，把当前值向 reaction 推近，最后略微向基线调节。

人格参数目前是代码中的常量。模型评价时会收到整个参数字典；数值公式中实际直接使用 sensitivity、extraversion 和 conscientiousness，不是每个参数都单独进入规则。

## 7. 记忆系统：从原话到经历，再到认识

这是逻辑最多的模块。第一遍先读 [数据模型](agent/systems/memory/domain/models.py)，然后按下面的小节逐个看 [MemoryService](agent/systems/memory/application/service.py)，不必一次读完整个服务。

### 7.1 三层数据与三种节点不是同一个分类

三层数据指：

| 层次 | 实现 |
| --- | --- |
| 完整历史 | messages 表保存逐条真实发言 |
| 短期窗口 | 本轮临时从当前会话历史中取出的近期原话 |
| 长期记忆 | SQLite 中的记忆节点及关系，以及 Chroma 中 event/thought 的检索索引 |

长期节点又分三种类型：

| type | 含义 | 例子 |
| --- | --- | --- |
| chat | 这一批交流的记录节点，通过来源 ID 连接实际原话 | 一批关于图书馆的交流 |
| event | 从交流提炼的、值得保留的信息 | 用户表示图书馆三楼靠窗处安静 |
| thought | 根据多条事件归纳的认识 | 用户可能重视安静的阅读环境 |

chat 节点的 description 只是“交流：”加上部分用户文本，完整正文应通过消息来源读取。chat 不进入向量索引，当前长期检索使用 event 和 thought。

### 7.2 正文、关系、保留状态分开

`MemoryNode` 保存描述、时间、有效性、重要性、关键词、背景、标签等。`RetentionState` 单独保存强度、稳定性、时间基准和回忆次数。

三种 ID 关系也有不同语义：

```text
source_message_ids    这条记忆来自哪些实际消息？
evidence_memory_ids   这条认识依据哪些记忆？有方向。
related_memory_ids    哪些记忆语义相关？普通双向关联。
```

例如 thought 可以通过 evidence 找到 event，再通过 source 回到用户原话。实际存储时，thought 也保留从证据事件汇总而来的来源消息 ID。

### 7.3 recall()：怎样找到相关记忆

`recall()` 的步骤是：

1. 向 Chroma 查询相似候选，默认最多 20 条。
2. 从 SQLite 获取正文和保留状态，过滤过期或失效节点。
3. 按相关性、重要性、近期性打分，取前 5 条。
4. 扩展这些节点的证据和普通关联，最多合计 8 条。
5. 附带本轮强度、清晰度和选中原因，记录 retrieval 日志。

当前评分：

```text
score = 0.75 × max(0, similarity)
        + 0.15 × importance / 10
        + 0.10 × exp(-days / 30)
```

这里 days 从保留状态的 `anchor_at` 计算；初次形成时它是初始化时间，强化后会重置，因此不固定等于距创建时间的天数。

记忆强度没有直接乘进评分。低强度记忆仍可能被检索到，清晰度再交给回复模型参考。

### 7.4 remember()：怎样形成新记忆

这个方法依次做几件事：

1. 保存 chat 节点，引用本批用户消息及实际回复；没有回复时只引用用户消息。
2. 调用模型生成 `Formation`：最多 3 条新事件，最多 5 个邻居更新，也可以都为空。
3. 校验关联 ID、纠正目标 ID 和邻居更新 ID 是否来自提供的候选。
4. 保存 event，用注意力、情感冲击、重要性初始化保留状态。
5. 更新旧邻居的 context 和 tags，保留旧事实正文。
6. 更新向量索引，再尝试反思。

候选邻居来自本轮检索。当前没有在每次形成记忆时扫描所有历史节点、让模型任意改写整个记忆网络。

### 7.5 reflect()：什么时候形成认识

同时满足以下条件才触发反思：

- 本轮形成了新事件。
- 待反思事件涉及至少两条不同的来源消息 ID；代码用它计数观察来源，不按批次数计算。
- 待反思事件数量至少 3 条，或者重要性之和至少 15。

每次最多取 12 条符合条件的待反思事件，模型最多生成 2 条 thought。每条 thought 至少引用两个不同的有效候选记忆 ID。

模型允许返回空 thoughts。完成后候选事件仍会标记为已反思，所以“反思已处理”不表示一定生成了新认识。

当前反思主要从 event 归纳，尚未形成任意多层认识不断递归反思的流程。

### 7.6 衰减和强化怎样计算

规则在 [ebbinghaus.py](agent/systems/memory/engines/ebbinghaus.py)。

初始化：

```text
initial_strength = 0.3 × attention
                   + 0.3 × emotional_impact
                   + 0.4 × importance / 10
stability_days = 1 + 89 × initial_strength
```

当前强度：

```text
strength = strength_after_recall × exp(-流逝天数 / stability_days)
```

例如注意力 0.8、冲击 0.5、重要性 8，初始强度为 0.71，稳定性为 64.19 天；没有强化时，30 天后的强度约为 0.445。这只是当前工程公式的示例。

`views()` 把强度大于 0.6 映射为“清晰”，大于 0.2 且不超过 0.6 为“模糊”，其余为“淡忘”。当前仍把完整描述连同清晰度交给模型，尚未在程序层按强度删除描述中的细节。

`record_usage()` 只处理对话输出中报告采用、且确实属于本轮候选的记忆 ID。强化会增加回忆次数，根据距上次基准的间隔调整稳定性和基准强度，再重置 `anchor_at`。

因此要区分“进入候选”“模型报告采用”“用户感受到回答用了往事”这三件事。当前采用登记依赖回复模型的结构化报告。

### 7.7 失效与淡忘怎样区分

`supersedes_id` 用于明确纠正旧认识：保存新节点时，将旧节点标记为 superseded。正常随时间变化不等于旧事实错误。

失效、过期会影响是否能作为有效回忆；低强度本身不会把节点标记为失效。

thought 的有效性依赖证据；证据失效时，该 thought 不再作为有效回忆。它的有效强度也受证据约束，取自身与证据强度中的最小值。

## 8. 对话系统：把已有信息组织成回答

读 [DialogueReply](agent/systems/dialogue/domain/models.py)、[DialogueService](agent/systems/dialogue/application/service.py) 和 [提示词](agent/systems/dialogue/prompting/builder.py)。

核心输入包括人物状态、候选更新后的情绪、近期原话、本批消息、长期回忆、当前时间和 Planner 给出的回复方向。

输出只有两部分：

```json
{
  "answer": "实际发送的回复正文",
  "used_memory_ids": []
}
```

只使用当前消息或近期原话时，used_memory_ids 可以为空。这个数组用于登记真正采用的长期记忆，不填写消息 ID。

`generate()` 只调用一次回复模型，并检查返回的记忆 ID 是否属于本轮长期回忆候选。它自己不更新情绪，不写消息历史，也不强化记忆；后面的提交和强化由 Runtime 组织。

## 9. 数据保存在哪里，模型由谁调用

### 9.1 SQLite 是主数据，Chroma 是检索索引

读 [database.py](agent/infrastructure/persistence/database.py) 和 [chroma_index.py](agent/infrastructure/persistence/chroma_index.py)。

| 保存位置 | 内容 |
| --- | --- |
| messages | 完整真实发言 |
| memories | 记忆正文、语义字段、事实有效性、索引状态 |
| memory_sources / memory_evidence / memory_links | 原话来源、反思证据、普通关联 |
| memory_retention / memory_processing | 保留状态、关联和反思处理进度 |
| character_states / emotion_states | 人物状态和情绪快照 |
| turns / events | 处理结果、阶段日志、结构化输入输出 |
| runtime_settings | 模拟时间偏移 |
| Chroma | event/thought 的向量、可检索文本及少量元数据 |

实际路径是 `storge/sqllite/history.sqlite3` 和 `storge/chromadb`。路径拼写与代码保持一致。

Chroma 用“描述 + 背景 + 关键词”构造嵌入文本，按角色 ID 过滤检索，因此同一角色的新会话仍可使用以前的长期记忆。新会话的近期原话窗口则从自己的历史开始。

SQLite 与 Chroma 的更新不是一个跨库事务。向量更新失败时，SQLite 中已经保存的记忆会保留，索引状态标为 failed，可以重试。

### 9.2 统一模型网关

[llm/models.py](agent/infrastructure/llm/models.py) 把业务模型调用统一为：

```text
model.ask(输出类型, 指令, 上下文, purpose)
```

`purpose` 区分 reply_planner、emotion、dialogue、memory_formation、reflection。

网关读取 agent-system/.env，通过 LangChain 的 OpenAI 兼容接口调用服务；这表示接口协议，不限定必须使用某一家模型。

调用时约束返回 JSON，再用 Pydantic 数据模型校验字段和范围。公共 Model 默认禁止额外字段以及 NaN、无穷大数值。模型输出失败会报错，不会自动替换模型或重复重试。

### 9.3 统一时间

[common/models.py](agent/common/models.py) 使用固定 UTC+08:00 的北京时间。`Runtime.now()` 在真实北京时间上加数据库保存的模拟天数偏移。

`advance()` 修改偏移并记录衰减和情绪变化，不改历史消息时间。记忆强度在读取时计算，不需要后台每秒写一次衰减结果。

推进时间本身不会让“最近 12 条消息”自动退出窗口。观察长期记忆遗忘时，应推进时间后新建会话，避免答案仍来自清晰的近期原话。

## 10. 用日志和测试辅助理解

### 10.1 先观察一次真实交流

按 [README 启动说明](README.md#启动) 启动服务和已有前端后，可以先发送一条关于阅读经历的消息，在记忆实验室的“变化记录”里找这些阶段：

| 阶段 | 要观察什么 |
| --- | --- |
| planner_decision | 本轮为什么回复、等待或跳过 |
| retrieval | 找到了哪些长期回忆，为什么入选 |
| emotion_appraised | 旧情绪、候选情绪和本次冲击 |
| attention | 本轮注意力及计算依据 |
| context | reply 分支真正交给回复模型的上下文 |
| emotion_updated / reply_saved | 哪些结果已经提交 |
| reinforcement | 哪些旧记忆真正登记了采用 |
| memory_created / association_updated | 新事件与旧邻居发生了什么变化 |
| reflection_waiting / reflection_complete | 是否达到反思条件，以及实际新增数量 |

这些记录是可观察的阶段输入输出，不是模型隐藏思维过程。第一轮没有旧记忆时，检索为空、没有强化日志都可能是正常情况。

### 10.2 再读确定性的离线示例

[test_runtime.py](tests/test_runtime.py) 的 `OfflineModel` 根据 purpose 返回固定结构，`OfflineIndex` 提供可控检索，测试用临时目录保存数据。通过它们可以先理解程序流程，不必依赖真实模型的随机输出。

推荐优先阅读：

| 测试 | 理解目标 |
| --- | --- |
| test_full_turns_sources_association_reflection_and_actual_recall | 来源、关联、反思和实际采用怎样连接 |
| test_time_decay_emotion_recovery_and_history_unchanged | 推进时间怎样影响记忆和情绪，历史怎样保留 |
| test_state_changes_attention_and_recent_window_is_conversation_local | 状态如何影响注意力，以及会话窗口边界 |
| test_index_failure_preserves_answer_and_can_retry | 回复已成功、索引失败时怎样保留结果 |

随后读 [test_reply_coordinator.py](tests/test_reply_coordinator.py)，重点看连续消息合批、wait 唤醒、skip 不伪造回复、旧批回复和情绪被丢弃的场景。

如果要执行现有离线测试，在 studyAgent 根目录运行：

```powershell
uv run python -m unittest discover -s agent-system/tests -v
```

这些测试验证程序约束和数据流；真实模型是否合理评价情绪、提炼事实或生成认识，仍需要结合实际交流观察。本文编写过程没有执行该命令，也没有调用真实模型。
